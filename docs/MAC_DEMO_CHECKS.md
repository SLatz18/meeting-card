# Mac demo checks (run by hand on a real Mac, with the user's go-ahead; not CI tests)

## Always the test build (`--test-id`)
Every check below runs on the **test build**, never the real app, so the real app's privacy grants, settings and
Keychain item are never touched. Get it either way:
- `swift/scripts/build.sh --test-id` installs `~/Applications/MeetingCardSwift-Test.app` (not launched);
  `swift/scripts/build.sh build --test-id` only builds it, in `swift/build/dd-test/Build/Products/Release/`.
- or the unsigned `MeetingCardSwift-Test-app` CI artifact (see [SIGNING_PLAN.md](SIGNING_PLAN.md) for opening it).
  The `MeetingCardSwift-app` artifact is the real app: don't use it for these checks.

The test build has its own identity, and nothing else changes:

| | Real app | Test build |
|---|---|---|
| Bundle ID | `com.slatz.meetingcard.swift` | `com.slatz.meetingcard.swift.test` |
| Name in permission prompts and System Settings | MeetingCardSwift | MeetingCard (Test) |
| UserDefaults domain | `com.slatz.meetingcard.swift` | `com.slatz.meetingcard.swift.test` |
| Keychain service (account `OPENAI_API_KEY`) | `com.slatz.meetingcard.swift.openai` | `com.slatz.meetingcard.swift.test.openai` |
| Log | `~/Library/Logs/MeetingCardSwift.log` | `~/Library/Logs/MeetingCardSwift-Test.log` |
| State | `~/Library/Application Support/MeetingCardSwift/` | `~/Library/Application Support/MeetingCardSwift-Test/` |
| Saved transcripts (Save transcripts on, default folder) | `~/Library/Application Support/MeetingCard/Transcripts/` | `~/Library/Application Support/MeetingCard-Test/Transcripts/` |
| Login item | `~/Applications/MeetingCardSwift.app` only | never |

macOS asks for Microphone and Screen & System Audio Recording again for "MeetingCard (Test)"; grant them there.

**Quit the real app before checking** (`pkill -f MeetingCardSwift.app/Contents/MacOS/MeetingCardSwift`; it doesn't
match the test build). Both builds read the same calendar, so both would show cards, and with the coach on in both,
both would react to the same call. The coach's unified-log entries (`com.listenmore.kit`, K1) also come from a
process named `MeetingCardSwift` in either build.

Clean up after the demo (only the test identity; the real app is untouched):
`tccutil reset Microphone com.slatz.meetingcard.swift.test` (likewise `AudioCapture`, `ScreenCapture`, and `Accessibility`, `AppleEvents` after the Zoom/Meet checks),
`defaults delete com.slatz.meetingcard.swift.test`,
`security delete-generic-password -s com.slatz.meetingcard.swift.test.openai -a OPENAI_API_KEY`,
`rm -rf ~/Library/Logs/MeetingCardSwift-Test.log ~/Library/Application\ Support/MeetingCardSwift-Test`.

## Checks
Prereqs: the test build (above);
coach turned on in MeetingCard Settings (or the coach menu bar menu) with an OpenAI key, except for L1/L2; Microphone and Screen & System Audio Recording granted when
macOS asks. If a call app's bundle ID differs from `capture_targets` in
`swift/Packages/ListenMoreKit/Sources/ListenMoreCore/DefaultConfig.swift` (`osascript -e 'id of app "<App>"'`), note it.

The coach starts from Core Audio state only: the call app producing output and the microphone running, for about 3 s.
With **Use Zoom/Meet controls** on (checks ZC*, MC*, MD*), Zoom's meeting controls and an open Meet tab also end it
about 3 s after the call ends and hold it while Zoom is muted. **Meet mute is not detected** (in Chrome or Dia): it
isn't readable without page content, so muting in Meet never pauses the coach (MC4). Only Zoom's mute does.
The indicator is the coach card (the reminder card morphs into it near the camera; it can be minimized to a pill), showing
Coach on → Coach on, listening → Coach paused, and the status line of the coach menu bar menu, which is always there (Start
Coach while off).

### Audio debug readout (test build only)
In the test build only, hold Option while the coach menu bar menu is open: **Settings…** turns into
**Audio Debug Readout…**. It opens a small window that refreshes every second and records nothing (no file, no log).
The real app has none of it. It shows:
- the coach indicator, and whether it is capturing;
- the mic: open, closed or muted; whether the engine is running or stopped; and the restart count;
- the **Route** (speakers, wired headphones, Bluetooth, or other) with the output connection class (builtIn,
  bluetooth, usb or other; a USB headset counts as speakers, so voice processing is on, and this is how to tell them
  apart), the **Mic source** (system default, built-in or
  none) and **Voice processing** as planned;
- voice processing and other-audio ducking as applied by the running engine: advanced on or off, and the level
  with its raw value (min = 10);
- the **Mic device** line: the requested device, what the engine reports, and the device actually in use, read back
  from Core Audio, followed by "(matches the request)" or "(not the requested mic)";
- a **Set aside (delivered no sound)** line, only when the coach has set the built-in mic aside (see LID1);
- the Speaker mic diagnostics values (below);
- the default input device: name, transport (Built-in, Bluetooth, USB…), sample rate, and whether it is running somewhere;
- the default output device: name, transport, data source (Internal Speakers or Headphones, when reported), sample
  rate, and device volume (0 to 1);
- **Output call state**: the default output's transport (raw: builtIn, bluetooth, usb, other, or none), whether its input stream is active (yes, no or unknown; unknown when the headset's mic is not part of the output device or cannot be read), its sample rate in Hz (or ?), and **call mode** (yes or no: what the coach card's call-mode tip is based on: it shows only when the output's own input stream is active and its sample rate is 24 kHz or below, and stays silent when that cannot be decided; n/a when the coach is off and the mic does not exist);
- **Mic in use by**: the bundle IDs of the processes running audio input.

The test build's coach menu also shows a **Mic: …** line under its status line, for example
`Mic: MacBook Pro Microphone (built-in) · voice processing off · bluetooth (bluetooth)`. It names the device actually in
use. With no mic it reads `Mic: none, call audio only · …`, plus `(built-in mic gave no sound)` when the built-in mic
was set aside.

**Speaker mic diagnostics** is a hidden switch in this window, test build only. It has two controls:
- **Speakers: voice processing**: Standard, On or Off (Standard is the shipping behavior: voice processing on).
- **Speakers: mic source**: System default or Built-in mic.

It applies at once (the mic reopens), affects the speakers route only (headphones and Bluetooth output ignore it),
and is not saved: it resets when the app quits. The shipping app has none of it. Standard is the shipping
behavior: voice processing on with other-audio ducking at its minimum, using the system's input (the built-in mic
instead if the system input is Bluetooth).

### Cue display prototype (test build only)
The test build's coach menu bar menu also has **Cue Display Prototype…** (under Settings…): a window that plays
recorded and synthetic cue timelines through the coaching-display options, on the coach card or the pill, so they
can be compared without a call (check CD1, [COACHING_DISPLAY.md](COACHING_DISPLAY.md)). It plays fixed timelines
only: no audio, no session, nothing saved. The real app has none of it.

### Logic covered by the Linux harness
`swift/Packages/ListenMoreHarness` runs the coach's real pipeline on Linux with synthetic You (mic) and Them (call)
streams: offline in CI on every pull request, and live with OpenAI TTS on demand (see its README). The rows marked
**logic covered by harness** have their logic asserted there, so they don't need a full hand pass every time:
- **MU1's caption checks**: while muted, no You lines in the captions or the saved transcript and Them captions keep
  coming; after Unmute, You lines return and no red cue fires in the first seconds (`local.unmute_grace_s`). The rest
  of MU1 (Control Center's microphone list, the card, pill, chip and menu wording, Zoom's or Meet's own mute, Pause
  and Resume keeping the mic off, the next call starting unmuted) stays a hand check.
- **X1, X3, X4** (there is no X2): captions labelled You and Them, at most three lines, gone when the call ends; no key
  means no captions; a name for Them shows in the captions and the saved file and is back to Them next call. Only the
  logic: X1's look in the card and the Saving transcript badge are in the CI coach-card snapshots and the smoke row.
- **T2–T5**: saving off writes nothing; saving on writes exactly one `<date> <time> <title>.md`, mode `-rw-------`, with
  times and speaker labels and no audio; Delete during a call and after it; the cost cap stops captions while local
  cues still fire.

What the harness can't see (real capture, macOS permissions, the card on screen, the unified log) stays with one
short hand row before demo sign-off: **CS1, the Mac caption smoke (X1 + MU1 + K3)**.

### Keychain caveat (read before K1/K2)
The app asks for the key to be kept "on this device only, while unlocked" (`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`).
The current build stores it in the login keychain, which ignores that setting. The setting only takes effect in a
properly signed build that uses the data-protection keychain (the `keychain-access-groups` entitlement, which needs an
Apple developer account; see [SIGNING_PLAN.md](SIGNING_PLAN.md)). Until then:
- the key does **not** sync to other devices through iCloud Keychain;
- the key **can** move to another Mac in a Time Machine backup or a Migration Assistant transfer.

If that matters for the demo Mac, remove the item after the demo (Keychain Access, or
`security delete-generic-password -s com.slatz.meetingcard.swift.test.openai -a OPENAI_API_KEY`).
